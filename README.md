Задание 1
Опишите основные преимущества использования масштабирования методами:

активный master-сервер и пассивный репликационный slave-сервер;
master-сервер и несколько slave-серверов;
Дайте ответ в свободной форме.


Один slave (активный master + пассивный standby)

Простая схема
Быстрый failover при падении мастера
Горячая копия данных
Бэкапы без нагрузки на основной сервер

Несколько slave (master + read replicas)

Масштабирование чтения (горизонтально)
Сильная разгрузка мастера от SELECT-запросов
Высокая доступность чтения (реплики могут падать)
Геораспределение и аналитика на отдельных серверах

Первый вариант — в основном про надёжность.
Второй — про производительность при большой нагрузке на чтение.



Задание 2
Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц:

пользователи,
книги,
магазины (столбцы произвольно).
Опишите принципы построения системы и их разграничение или разбивку между базами данных.

Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера.

Вертикальное разделение (каждая таблица на своём сервере/кластере):

Сервер 1 → только таблица users
Сервер 2 → только таблица books
Сервер 3 → только таблица stores

Горизонтальное разделение (шардинг) делаем только когда данных/нагрузки станет очень много. Пока можно начать без него.

Как работает приложение

- Хочешь посмотреть/изменить профиль пользователя → идёшь на Сервер Users
- Ищешь книгу, добавляешь книгу → идёшь на Сервер Books
- Показываешь магазины, добавляешь магазин → идёшь на Сервер Stores

Если нужно связать данные (например, «какие книги у пользователя»):

- Сначала берёшь user_id с сервера Users
- Потом по этому user_id идёшь на сервер Books и ищешь книги

Режимы серверов (очень просто)

- Master — единственный, кто может писать (добавлять, менять, удалять)
- Slave (1–2 штуки на каждый master) — только для чтения + копируют данные с мастера
  → если master упал → один из slave становится новым master
  → все тяжёлые чтения (списки, отчёты) отправляй на slave

Когда добавлять горизонтальный шардинг
Только если одна таблица вырастет огромной (сотни миллионов строк или нагрузка > того, что тянет один сервер):

- users → делим по user_id (чётные / нечётные, или по хэшу)
- books → делим по user_id (чтобы книги одного пользователя были на одном сервере)
- stores → делим по id магазина или по городу/стране

Но на старте и при среднем объёме данных — вертикального разделения + реплик (master + slave) обычно хватает на годы.
